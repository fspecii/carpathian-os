# Carpathian Reminders

A local GTK3 reminder manager with title, optional notes, optional due date/time, edit, completion/reopen and deletion. Data is shared by GUI and CLI in `$XDG_DATA_HOME/carpatic/reminders/reminders.json` (default `~/.local/share/carpatic/reminders/reminders.json`). It never writes to calendar ICS files, uses no accounts/network, and the editor starts no daemon automatically. A separate Gio-only notifier delivers timed due alerts through the local freedesktop notification server.

## Run and integration

Run `bin/carpatic-reminders` from this directory or use the installed `carpatic-reminders`. Python3 and GTK3/PyGObject are runtime requirements (Alpine: `python3 py3-gobject3 gtk+3.0`). The active Carpathian Settings palette is reused when that component is present; otherwise the app uses its original neutral light palette and system widgets. No proprietary artwork or upstream theme assets are included.

`install.sh` installs only program files and an application menu entry. `DESTDIR=/absolute/staging/path ./install.sh` supports reviewable staging without touching the running OS. The Alpine desktop-tools installer includes this component, and the managed Carpathian session hook starts its notifier; standalone installation remains inert.

Calendar's selected-date link opens `carpatic-reminders --date YYYY-MM-DD`; its Add button opens `carpatic-reminders --date YYYY-MM-DD --new`. The app uses `org.carpatic.Reminders` for single-instance GTK/GApplication routing. The flyout reads pending counts using the same CLI/store on a delayed worker thread, with a two-second timeout and a bounded result. There is one reminder store and no synchronization copy. Opening another app/date reloads the list. The calendar count is refreshed on flyout open/date change, not continuously while idle; a changed store in an already-open flyout requires reopening the flyout.

CLI examples:

```sh
carpatic-reminders add 'Buy groceries' --due-date 2026-10-11 --due-time 17:30
carpatic-reminders list --pending --date 2026-10-11
carpatic-reminders edit UUID --title 'Buy groceries and bread' --due-time ''
carpatic-reminders complete UUID
carpatic-reminders complete UUID --reopen
carpatic-reminders delete UUID
```

The `list` command emits a JSON array, with stable version-1 records (`id`, `title`, `notes`, `due_date`, `due_time`, `completed`, `created_at`). Mutation commands print their result as JSON; errors use stderr/nonzero status. Dates use `YYYY-MM-DD`, times `HH:MM` with a date. Empty edit date clears both date and time. Empty edit time clears just the time. No GUI toolkit is loaded for CLI calls.

## Storage and interaction

Writes use a process lock (two-second contention limit), a same-directory mode-0600 temporary file, fsync and atomic replacement; readers see a complete old or new document. Invalid/corrupt data is rejected and preserved. Limits: 1 MiB file, 1000 records, 200-character title, 4000-character notes. All GUI storage operations run in one worker; no per-frame I/O or periodic idle timer. Save failures stay visible in the editor. Multiple CLI/process writers serialize their read-modify-write operations.

Select a row to edit it, toggle its checkbox to complete/reopen, or use the editor. Ctrl+N starts a new reminder; Ctrl+S saves; Ctrl+R refreshes. Standard GTK Tab/Shift+Tab traverses controls. Date/time fields have explicit input hints and validation. Completed items are hidden by default and can be shown. The current initial editor has no unsaved-edit recovery or undo deletion; these remain polish tasks. Repeat schedules, explicit time-zone scheduling, import/export and synchronization are separate next stages.

## Optional timed alerts

`carpatic-reminders notify-service` runs the notifier on the user's session bus. It uses Gio/PyGObject without importing GTK. **The standalone component installer does not start this service or install autostart entries**. The Alpine desktop-tools installer includes the component; the managed Carpathian login hook starts the notifier on its private session bus. Integrated login acceptance is a separate lead gate. The GTK editor does not start the notifier secretly. Its hint distinguishes this dependency.

Only pending reminders with **both a date and a time** alert; date-only and undated tasks do not alert. Timed overdue reminders alert once when the notifier starts. A Gio directory monitor reloads edits/completion/deletion off the event loop, and one next-deadline GLib timer is armed. While scheduled undelivered items exist, deadline revalidation is capped at 60 seconds to detect wall-clock changes and resume drift; an empty, completed-only or fully delivered store has no periodic timer. Detection after a clock/time-zone change or resume is within the next revalidation interval plus delivery/queue time, not a hard real-time guarantee.

Dates/times are interpreted in the **current local system zone**, not stored UTC instants. The first occurrence (`fold=0`) is chosen for an ambiguous autumn DST time. A nonexistent spring time moves forward by the transition gap (e.g. Bucharest 03:30 becomes 04:30 that day). Changing the system zone recalculates still-pending due instants at revalidation. Already delivered wall-time signatures stay delivered. These explicit policies avoid an unstated exact-time claim; per-reminder zones are future work.

One mode-0600 lifetime lock beside the shared store prevents concurrent notifier instances across login sessions using that store. `delivery-ledger.json` is a separate atomic mode-0600 ledger keyed by reminder id and due-date/time signature; it does not modify editable reminders. A normal restart does not duplicate accepted alerts. Editing the title/notes alone does not resend; changing date/time establishes a new schedule. Completing and reopening an already delivered reminder does not resend unless its due schedule changes. Deletion cancels pending delivery. The worker revalidates a reminder immediately before a send, although a change racing an already accepted server call cannot retract that notification.

The service observes its actual session-bus connection's `closed` signal even with an empty queue. Gio's automatic process exit on bus closure is disabled so shutdown can finish an already accepted delivery's ledger transaction. Bus closure or SIGTERM/SIGINT/SIGHUP cancels the timer/monitor and prevents further batch sends; the bounded worker finishes before the lifetime lock is released. If the notification capability request completes after cancellation, Notify is not sent. A new instance waits up to eight seconds using bounded sleeping backoff for an old instance to release its lock. Persistent contention prints a diagnostic and exits **75**, rather than claiming it started successfully; it never kills another process or steals the lock. A session manager must still terminate the notifier on logout when a user's bus itself persists across sessions. Real logout/autostart acceptance belongs to the lead's isolated session test.

The notification request uses typed D-Bus fields and escapes body text when the server advertises markup; plain-text servers receive plain text, never shell interpolation. It checks capabilities and sends Notify using the [freedesktop notification protocol](https://specifications.freedesktop.org/notification/latest/protocol.html). Each D-Bus call has a 1500 ms timeout; a cycle attempts at most three alerts. Failed delivery does **not** mark a reminder delivered, and retries use 5/30/120/300-second bounded backoff. Restart resets backoff and retries undelivered overdue tasks. A ledger failure pauses further sends until persistence succeeds. Corrupt ledgers are preserved and prevent service startup rather than silently forgetting delivery state.

There is an unavoidable crash boundary: a notification server may accept a request before the process can persist its ledger, so a crash or disk failure then restart can repeat that alert. Likewise a server accepting a request means delivery was accepted, not that the user saw it (DND, lock screen or server policy can suppress it). The implementation makes **no exact-once or physical visibility claim**. Retained file monitors, one executor thread and no idle timer for an empty queue are architectural properties; memory/CPU savings remain to be measured.
